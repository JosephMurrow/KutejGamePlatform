# База

PostgreSQL 17, Prisma 7. Схема разложена по файлам:
`prisma/schema/platform.prisma`, `prisma/schema/pricetitute.prisma` и
`prisma/schema/chess.prisma`.

## У каждой игры своя схема

```
platform     users · one_time_links · private_rooms
pricetitute  questions · rounds · round_bets · scores · room_question_queues
             room_settings
chess        room_settings · matches · openings · ratings · pairs
public       только _prisma_migrations
```

**Имена моделей Prisma глобальны — схема Postgres их не разводит.** Две игры
не могут обе назвать модель `RoomSettings`, хотя таблицы у них лежат в разных
схемах и не встречаются: генератор откажется. Поэтому модель и перечисления
игры начинаются с её кода — `ChessRoomSettings`, `ChessTimeControl`, — а
таблица через `@@map` зовётся коротко: `chess.room_settings`. Платитутка
успела занять простые имена первой, и трогать их незачем.

**Почему схемы, а не отдельные базы.** Игровые таблицы ссылаются на
пользователя внешними ключами: `scores.userId`, `rounds.hostId`,
`round_bets.playerId`. Между базами ссылочной целостности нет, и «кто этот
игрок» пришлось бы выяснять вторым запросом руками. Схемы дают ту же
изоляцию — свои имена, свои права, отдельный дамп — и ключи при этом живут.

**Чем ссылаться на комнату.** Строкой без внешнего ключа: так у `rounds`,
`scores`, `room_question_queues` и `room_settings`. Причина историческая и
рабочая: ключ комнаты бывает литералом общего зала, которому строки в базе не
соответствует. Убирает эти строки сама игра, когда платформа сообщает ей об
удалении комнаты.

## Платформенные таблицы

| Таблица          | Что                                | Заметки                                                               |
| ---------------- | ---------------------------------- | --------------------------------------------------------------------- |
| `users`          | аккаунты, гости и боты             | `isBot` — игровой флаг в платформенной таблице, осознанный компромисс |
| `one_time_links` | подтверждение почты и сброс пароля | хранится SHA-256, живёт час                                           |
| `private_rooms`  | комната как оболочка               | `gameId` говорит, во что тут играют                                   |

В `private_rooms` нет ни одной игровой колонки: тайминги фаз, режим вопросов,
ротация ведущего и условие конца партии живут в схеме игры.

## Миграции

18 штук, применяются отдельной командой после запуска, а не на старте
процесса: при нескольких инстансах они подрались бы за одну и ту же миграцию.

```bash
npm run db:migrate          # разработка: migrate dev + generate
npx prisma migrate deploy   # бой
npx prisma migrate status   # что применено
```

**Две миграции написаны руками, и это важно понимать.** Автогенератор на
переносе таблиц между схемами и на переезде колонок выдал бы `DROP` и
`CREATE`, то есть снёс бы содержимое. `ALTER … SET SCHEMA` и явный `INSERT …
SELECT` переносят данные, ничего не переливая насмерть:

- `20260908120000_schemas_per_game` — таблицы разъехались по схемам;
- `20260908160000_game_room_settings` — настройки партии уехали к игре.

Прежде чем закладываться на возможности Prisma — проверь их на этой версии.
Несколько схем, папка схем и ссылка платформенной таблицы на игровой enum
работают без preview-флагов; это проверено, а не взято из документации.

## Клиент

Генерируется в `src/generated/prisma`, **не коммитится**, делается
`postinstall`. Путь вывода в схеме относительный — при переезде схемы он
съезжает, это уже случалось.

`src/lib/prisma.ts` — синглтон через `globalThis` и ленивый прокси: иначе
`next build` требовал бы живой базы.

## Сид

`prisma/seed.ts` — платформенный: идёт по реестру сидов и зовёт сид каждой
игры. Порядок фиксированный, платформенный первым (сеять ему пока нечего —
аккаунты заводят люди).

```bash
npm run db:seed
```

Сид каждой игры обязан быть идемпотентным: два прогона подряд не плодят
строки. У платитутки это `createMany` со `skipDuplicates`, а ключом служит
текст вопроса — отсюда отдельный порядок при выкладке, см.
[DEPLOY.md](./DEPLOY.md).

## Бэкап

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U platitutka -d platitutka --format=custom > backup.dump
```

Перед любой миграцией, которая трогает существующие данные, — обязательно, и
плюс прогон на копии. Порядок расписан в [DEPLOY.md](./DEPLOY.md).
